# Приёмник событий с очередью обработки

Flask + SQLite. Очередь своя, на таблице `tasks`, без Celery/RQ/Huey.

## Запуск

```bash
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python run.py                                        # http://127.0.0.1:5000
```

Файл БД `events.db` создаётся автоматически в текущей папке. Обработчики-заглушки
падают с вероятностью 30%; её можно менять: `FAIL_RATE=0.7 python run.py`.

```bash
curl -i -X POST localhost:5000/webhook -H 'Content-Type: application/json' \
  -d '{"event_id":"abc-123","type":"payment_succeeded","payload":{"amount":100}}'
# 202 {"status":"queued"}; тот же запрос ещё раз -> 200 {"status":"duplicate"}

curl localhost:5000/stats
# {"events_by_type": {...}, "tasks_by_status": {"pending":0,"success":0,"failed":0,"skipped":0}}
```

## Тесты

```bash
pytest
```

Тесты не используют реальное время и потоки: `process_one(conn, handlers, now=...)`
принимает "текущее время" параметром, поэтому паузы между ретраями проверяются мгновенно.

## Структура

```
eventsvc/__init__.py   create_app: POST /webhook, GET /stats
eventsvc/db.py         схема и подключение к SQLite
eventsvc/worker.py     очередь: claim_next, process_one, поток Worker
eventsvc/handlers.py   заглушки обработчиков (с имитацией сбоев)
run.py                 запуск сервера и воркера
tests/                 pytest
```

## Принятые решения

**Две таблицы: `events` и `tasks`.** `events` хранит то, что пришло, `tasks` - состояние
обработки. Событие и задача создаются в одной транзакции, поэтому не бывает события без
задачи.

**Идемпотентность на уровне БД.** `event_id` имеет `UNIQUE`; вставка делается через
`ON CONFLICT DO NOTHING` внутри `BEGIN IMMEDIATE`. Дубликат определяется атомарно, без
гонки "проверил - вставил". Повтор возвращает 200, новое событие - 202.

**Статусы строго четыре** (`pending`, `success`, `failed`, `skipped`), как в задании.
Состояния "в обработке" нет, вместо него **аренда (lease)**: при взятии задачи воркер
сдвигает `next_attempt_at` на 30 секунд вперёд. Задача остаётся `pending`, но другие
воркеры её не видят. Если воркер умер, аренда истечёт и задачу возьмут снова.
Тот же `next_attempt_at` задаёт паузу между ретраями.

**Почему задача не зависнет в `pending`.** Счётчик `attempts` растёт при каждом *взятии*,
а не при ошибке. Если воркер умирает на каждой попытке, то после третьего взятия и
истечения аренды задача переводится в `failed`, а не берётся в четвёртый раз
(тест `test_worker_dying_on_every_attempt_...`). Ошибка обработчика на последней попытке
тоже ведёт в `failed`. Любой путь заканчивается в `success`, `failed` или `skipped`.

**Ретраи.** Максимум 3 попытки, паузы 1с и 2с (`BACKOFF_BASE * 2**(attempt-1)`).
Константы вынесены в `worker.py`.

**`skipped`** - для типа события, у которого нет обработчика. Повторять такое бессмысленно.

**Защита от "устаревшего" воркера.** Запись результата делается с условием
`WHERE status='pending' AND attempts=<моя попытка>`. Если аренда истекла, пока обработчик
работал, и задачу уже взял другой воркер, наш поздний результат его запись не затрёт.

**Ошибки валидации:** не JSON-тип - 415, битый JSON или не объект - 400, неверные поля - 422
со списком проблем в `details`. Лимит тела запроса 1 МБ.

**`time.time()` как "часы"** и время в БД как unix-timestamp: просто и достаточно для задачи.

## Что не сделано / ограничения

- **Семантика at-least-once.** Если обработчик завис дольше аренды, задачу может взять
  другой воркер, и она выполнится дважды. Настоящие обработчики должны быть идемпотентными
  (например, по `event_id`).
- **Нет таймаута обработчика.** Зависший обработчик блокирует единственный поток воркера.
  Лечится запуском обработчиков в отдельном процессе с таймаутом, я этого не делал.
- **Один поток воркера.** Код рассчитан на нескольких воркеров (взятие через
  `BEGIN IMMEDIATE`), но параллельный запуск нескольких воркеров я не тестировал.
- **Нет ручного повтора `failed`-задач, очистки старых данных и метрик.**
- **Системные часы (`time.time()`)** могут прыгнуть при смене времени в системе;
  в продакшене это стоило бы учесть.
- **Проверка этой сдачи.** В моём окружении не было возможности установить pytest, поэтому
  тесты я прогнал самодельной заглушкой, которая запускает те же функции (17 из 17
  проходят), а не настоящим `pytest`. Плюс отдельно проверил сервис живым воркером на
  12 событиях с `FAIL_RATE=0.6`: все задачи пришли в конечные статусы. Настоящий
  `pytest` стоит запустить у себя.
